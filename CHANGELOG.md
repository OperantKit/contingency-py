# Changelog

All notable changes to this project are documented in this file.
The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions are taken from git tags.

## [Unreleased]

### Added

- `Concurrent(punish_changeover=..., punish_directional=...)`: punishment of changeover responses. `punish_changeover` is one schedule shared by every changeover direction (with `FR(2)`, every second changeover overall is punished, whatever its direction); `punish_directional` is a `{(from, to): schedule}` mapping, one schedule per direction; the two cannot be given together. A changeover punisher receives a response only when the response confirms a changeover (the test that arms COD, so with `frco` the `frco`-th consecutive response on the new operandum); every other step is a time tick for it. When several punishers (per-operandum `punish` and a changeover punisher) fire on the same response, their magnitudes add up. A response punished by a changeover punisher has `changeover_punished` in `Outcome.meta`. It runs on the Rust engine (an older `contingency_core`, which would ignore the punishment, raises `ScheduleConfigError`). `from_dsl` builds it from `PUNISH(changeover)=S` and `PUNISH(a->b)=S` (no longer `ScheduleConfigError`), and from `Overlay(Conc(...), P, target=changeover)`, which runs the same as `Conc(..., PUNISH(changeover)=P)`; `target=changeover` over a non-`Conc` baseline, over a `Conc` that already punishes changeovers, and a `PUNISH(a->b)` naming a component the `Conc` does not have raise `ScheduleConfigError`. `to_spec` writes `punish_changeover: <spec>` and `punish_directional: [{"from", "to", "schedule"}, ...]` on the `Concurrent` spec, and the conformance spec builder reads them. New fixtures `compound/concurrent_punish_changeover.json` and `compound/concurrent_punish_directional.json`.
- `MatchingToSample(correction=...)`: correction trials. `True` repeats a baseline trial that ends incorrect (a wrong choice or a timeout) after the ITI until it is answered correctly; an int `N` (1 to `2**32 - 1`) repeats it at most `N` times, then draws the next trial. A repeated trial keeps the correct operandum, sample and comparison positions and draws nothing from the RNG; probe trials are not repeated. With correction active, `Outcome.meta` reports `correction_trial`. `from_dsl` passes the `correction` of `MTS(...)` (no longer `ScheduleConfigError`), `to_spec` writes `"correction": {"mode": "unlimited"}` or `{"mode": "bounded", "limit": N}` (nothing for `correction=false`), and the conformance spec builder reads it. `MatchingToSample.choice_timeout` is now public. New fixture `trial/mts_n2_seed7_correction1.json`.
- `contingency.schedules.Lag(n, length=1)`: differential reinforcement of response variability (Page & Neuringer, 1985). A unit is `length` consecutive responses read as their operanda, units do not overlap, and a unit is reinforced at its last response iff it differs from each of the previous `n` units (fewer while fewer have been emitted); unreinforced units stay in the comparison list, and `Lag 0` reinforces every unit; `n` and `length` go up to `2**32 - 1`. It runs on the Rust engine when `contingency_core` has it. `from_dsl` builds it from `Lag n` / `Lag(n, length=k)`, `to_spec` writes the spec `{"type": "Lag", "params": {"n", "length"}}` (no longer `SpecUnrepresentableError`), and the conformance spec builder takes `Lag`. New fixture `differential/lag_2_length_2.json`.
- `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md`, and a Support section in the README.
- `contingency.envs` (extra `gym`): `ScheduleEnv`, a Gymnasium environment that runs any `Schedule` as a free-operant session, and the registered IDs `contingency/FR-v0` and `contingency/FI-v0` (available after `import contingency.envs`).
- `contingency.to_spec` (in `contingency.bridge.spec`): translates a contingency-dsl AST to the JSON schedule spec of the conformance corpus, so that `build_schedule_from_spec(to_spec(ast))` behaves like `from_dsl(ast)`. DSL constructs the spec has no form for (`BO`, `Overlay(target=)`, non-IRT `Pctl`, `Adj(delay|amount)`, declaration-form `MTS(samples=)`) raise the new `SpecUnrepresentableError`, a subclass of `ScheduleConfigError`.
- `contingency/ConcVIVI-v0`: concurrent VI VI with changeover delay on operanda `left` and `right` (`mean_left`, `mean_right`, `cod`), with the `conc_vi_vi` factory in `contingency.envs.presets`.
- `core/`: a maturin project that builds the `contingency_core` extension module (the contingency-rs engine through PyO3) as the `contingency-core` wheel. contingency-rs is taken from GitHub at a fixed commit.
- `.github/workflows/wheels.yml`: builds the `contingency-core` wheel with maturin-action for Linux x86_64 (manylinux2014), macOS x86_64 and arm64, and Windows x86_64, imports each wheel that the runner can load in a clean venv, and uploads the wheels as workflow artifacts.
- Schedule spec: `Concurrent` takes `cod_directional` (`[{"from", "to", "cod"}, ...]`) and `punish` (`{operandum: spec}`), so directional COD and per-operandum punishment have a spec form. `to_spec` writes them for `COD(a->b)=x` and `PUNISH(k)=S`; the `PUNISH` directional and changeover forms are rejected as by `from_dsl`. New conformance fixtures `compound/concurrent_cod_directional.json` and `compound/concurrent_punish.json`.
- `contingency.engine`: `RustSchedule` and `from_spec` run a schedule spec on `contingency_core` behind the `Schedule` protocol, with this package's `Outcome`, `Reinforcer`, `ResponseEvent` and errors (`ValueError` becomes `ScheduleConfigError`, `RuntimeError` becomes `ScheduleStateError`). `from_dsl` takes `engine="python"` (default) or `engine="rust"`.

### Changed

- Documentation: the README, AGENTS.md, llms.txt, `docs/` and `conformance/README.md` describe this package as the Python package of the contingency-rs engine: contingency-rs runs the schedules, the conformance fixtures are their specification, and this package's classes wrap the engine. `docs/*/protocol.md` and the algorithm pages for RR, RI, RT, FI, VI, VR and `LimitedHold` no longer describe `rng.setstate` or the `_arm_time` / `_withdraw_and_rearm` hooks of the removed Python implementation. `contingency.helpers.fleshler_hoffman` stays: it returns the values that contingency-rs draws for VR, VI and VT, as a list.
- `MatchingToSample` and `GoNoGo` have no Python implementation any more: `step` / `reset` always run on the Rust engine, and `engine` is always `"rust"`. A consequence schedule that runs in Python (an object of your own that implements `Schedule`, a custom-step `ProgressiveRatio`, a `Percentile` with a non-IRT target or rank 0), one already stepped since its last reset, and the same object given twice raise `ScheduleConfigError` instead of keeping the schedule in Python. `Outcome.meta` no longer has `inner_meta` (the meta of the consequence schedule's outcome, which only the Python implementation copied).
- `geometric` `ProgressiveRatio` runs on the Rust engine, which now rounds the requirement half to even as `round` does (`core/` takes contingency-rs at that commit); the requirements are unchanged. A `geometric` `ProgressiveRatio` can now be a component of a compound or a trial-based schedule. A `ProgressiveRatio` over `arithmetic`, `geometric` or `richardson_roberts` whose `start` / `step` is beyond the Rust engine's integer width raises `ScheduleConfigError` instead of running in Python. A `ProgressiveRatio` over a custom step function still runs in Python.
- `Multiple`, `Chained`, `Tandem`, `Mixed`, `Concurrent`, `Alternative`, `Conjunctive`, `Overlay`, `Interpolate`, `SecondOrder`, `Timeout` and `ResponseCost` have no Python implementation any more: `step` / `reset` always run on the Rust engine, and `engine` is always `"rust"`. They take only components (and `Concurrent` punishers) that run on the Rust engine: a component that runs in Python (an object of your own that implements `Schedule`, a custom-step `ProgressiveRatio`, a `Percentile` with a non-IRT target or rank 0), a component already stepped since its last reset, and the same object given twice to one compound raise `ScheduleConfigError` instead of keeping the compound in Python. `LimitedHold` takes only `FI`, `VI` or `RI`; a schedule of another kind with `_arm_time` / `_withdraw_and_rearm` raises `ScheduleConfigError` instead of running in Python. When two `Concurrent` components deliver on the same tick, the one whose key sorts first wins (the order the Rust engine reads them), where the Python implementation took insertion order. `contingency/PunishedVI-v0` sets the punisher size on the outcome of the Rust-run `Overlay` instead of wrapping its punisher component; its rewards are unchanged.
- `FR`, `CRF`, `VR`, `RR`, `FI`, `VI`, `RI`, `FT`, `VT`, `RT`, `EXT`, `DRO`, `DRL`, `DRH`, `Lag`, `Sidman`, `DiscriminatedAvoidance`, `Escape`, `AdjustingSchedule` and `InterlockingSchedule` have no Python implementation any more: `step` / `reset` always run on the Rust engine, and `engine` is always `"rust"`. `RR`, `RI` and `RT` given a caller's `rng` now run on the Rust engine with a 63-bit seed drawn from that `rng` at construction (one `getrandbits(63)`, which advances it once), instead of running in Python and drawing from it on every step; the sequence of reinforcers differs from earlier releases for the same `rng`, and `reset` returns to the start of the new sequence. `rng=random.Random(s)` no longer draws the same sequence as `seed=s`; pass `seed=` for that. An `rng` without `getrandbits` raises `ScheduleConfigError`. `LimitedHold` around `FI`, `VI` or `RI` always runs on the Rust engine; `FI`, `VI` and `RI` no longer have the `_arm_time` / `_withdraw_and_rearm` hooks. `Percentile` keeps its Python implementation for a non-IRT target and for rank 0, which the Rust engine rejects.
- The schedule classes need `contingency_core`. Without it, or with a build whose schedules lack `Schedule.state()`, building any schedule class (also through `from_dsl` and `ScheduleBuilder`) raises `ScheduleConfigError` that says how to install the wheel from `core/`, instead of running in Python; so does a build without the correction trials of `MatchingToSample` or the changeover punishment of `Concurrent` when those are used. `import contingency`, parsing and `to_spec` work without it. Arguments the Rust engine rejects (integers beyond its integer width, infinite times, a negative `seed`) raise `ScheduleConfigError` instead of running in Python. The cases that stay in Python (a custom `ProgressiveRatio` step function, `Percentile` with a non-IRT target or rank 0) are unchanged. `core/` takes contingency-rs at a fixed commit that has `Schedule.state()`, and the `test` workflow builds the `contingency-core` wheel and installs it before running pytest.
- `from_dsl` keeps `engine="python"` as its default and returns the schedule classes, which run on contingency-rs when `contingency_core` is installed; `engine="rust"` returns the bare `RustSchedule`. `contingency-core` stays out of the package dependencies until its wheel is hosted on a package index. `tests/test_bridge_engine.py` checks the return type and the `engine` attribute of the default with and without the module.
- With `contingency_core` installed, `FR`, `CRF`, `VR`, `RR`, `FI`, `VI`, `RI`, `LimitedHold`, `FT`, `VT`, `RT`, `EXT`, `DRO`, `DRL`, `DRH` and `ProgressiveRatio` delegate `step` / `reset` to the Rust engine. Each instance has `engine` (`"rust"` or `"python"`). `RR`, `RI` and `RT` take a keyword `seed` (an int in `[0, 2**64)`, the same draws as `rng=random.Random(seed)`, not together with `rng`); a caller-supplied `rng` keeps the schedule in Python. `ScheduleBuilder.rr` / `ri` / `rt` take `seed`, and `from_dsl` and the conformance spec builder pass `@algorithm` seeds as `seed`. A `ProgressiveRatio` runs on the Rust engine over `arithmetic`, `geometric` or `richardson_roberts`. Unseeded VR, VI, VT, RR, RI and RT give the Rust engine a seed drawn at construction (VR, VI and VT draw a new one on each `reset`, as before). `Concurrent` asks a Rust-run component whether a response would reinforce through `RustSchedule.probe_response` instead of stepping a copy. `RustSchedule` supports `copy.deepcopy` by replaying its steps since the last `reset`. Errors raised while stepping on the Rust engine carry the Rust message text.
- With `contingency_core` installed, `Multiple`, `Chained`, `Tandem`, `Mixed`, `Concurrent`, `Alternative`, `Conjunctive`, `Overlay`, `Interpolate`, `SecondOrder`, `Timeout` and `ResponseCost` delegate `step` / `reset` to the Rust engine, building the spec from the components' specs (and the `Concurrent` punishers'); see the first entry of this section for components that cannot run there. Each instance has `engine`. Their position attributes (`active_index`, `current_stimulus`, `is_terminal`, `unit_completions`, `in_timeout`, `balance`) come from `RustSchedule.state()`; a `contingency_core` that lacks `Schedule.state()` raises `ScheduleConfigError`. `reset` resets the component objects and rebuilds the Rust schedule from them. A compound steps copies of its components, so the component objects (and attributes returning them) are not advanced by it.
- With `contingency_core` installed, `Sidman`, `DiscriminatedAvoidance`, `Escape`, `AdjustingSchedule`, `InterlockingSchedule`, `Percentile` (IRT target), `MatchingToSample` and `GoNoGo` delegate `step` / `reset` to the Rust engine, and read their changing attributes from `RustSchedule.state()`. Unseeded `MatchingToSample` and `GoNoGo` give the Rust engine a seed drawn at construction and a new one on each `reset`. Their `Outcome.meta` keeps the Python shape (`trial_outcome` always present, `choice=None` for a trial with trial types that ends without a named comparison, `comparisons` as a tuple).

- `from_dsl` and `to_spec` apply program-level parameter declarations instead of dropping them (`from_dsl`) or rejecting them (`to_spec`), without `contingency_dsl.analyze()`, so `@algorithm` seeds are kept: `LH` wraps every leaf base schedule that has no LH of its own (also inside `TO` and `ResponseCost`), except ratio schedules (`FR`, `VR`, `RR`, `CRF`, `PR`) and `EXT`, where an LH is vacuous; `COD` and `FRCO` are set on every `Conc` that does not set them, and `COD` becomes the symmetric base of a directional-only `COD(a->b)`. A program-level `RD` greater than zero raises `ScheduleConfigError` (the runtime has no reinforcement delay); `RD=0s` and `BO=0s` are accepted. For example, `LH = 2s` followed by `FI5s` now runs as `FI5s LH2s` instead of `FI5s`.
- `from_dsl` raises `ScheduleConfigError` for `Pctl` with any target other than `IRT` (`latency`, `duration`, `force`, `rate`, `location`, `amplitude`) when it builds the schedule, instead of building it and failing on the first `step()`. A postfix `LH` on `MTS` (`MTS(...) LH10s`, the form the grammar writes) is now the choice window in `from_dsl` and `to_spec`, the same as the keyword form `MTS(..., LH=10s)`, instead of a `LimitedHold` error (`from_dsl`) or a `LimitedHold` spec that the Rust engine rejects (`to_spec`); a postfix `LH` on `GoNoGo` raises the same `ScheduleConfigError` as `GoNoGo(..., LH=...)`, and an `MTS` / `GoNoGo` with more than one `LH` raises `ScheduleConfigError`.
- `from_dsl` raises `ScheduleConfigError` for `MTS` with `correction` and `GoNoGo` with `LH`, instead of running the schedule without them; `to_spec` raises the same error instead of `SpecUnrepresentableError`.
- `from_dsl` raises `ScheduleConfigError` for combinator parameters the runtime does not read, instead of dropping them: `BO` greater than zero on `Mult` / `Mix` (the runtime has no blackout), including a program-level `BO` declaration in a program with a `Mult` / `Mix`; `BO` on other combinators; `COD` / `FRCO` / `PUNISH` outside `Conc`; `Overlay(target=)`. Programs that were accepted before ran as if the parameter were absent. `BO=0` on `Mult` / `Mix` means no blackout and is accepted by `from_dsl` and written as no `BO` by `to_spec`.
- `Concurrent` COD now holds a reinforcer that a component sets up during the changeover delay and delivers it on the first response on that operandum after the COD, instead of discarding it; the component's next interval or ratio starts from that delivery (Herrnstein, 1961). Results of concurrent schedules with `cod > 0` differ from earlier releases. The conformance fixture `compound/concurrent_cod.json` is updated accordingly.

### Fixed

- `MatchingToSample` without a sample phase (`sample_duration=0`) reports `phase == "choice"` right after construction, as after `reset`, instead of `"sample"`.
- `Concurrent`: on a step where the COD holds the responded operandum's reinforcer, a reinforcer that another component delivers on its tick at the same step is returned (with `meta["cod_suppressed"]`) instead of being replaced by an empty outcome, unless a punisher fires at that step. New conformance fixture `compound/concurrent_cod_tick.json`.
- `Chained`, `Tandem`, `Multiple`: time-based components (FI, VI, RI, FT, VT, RT, DRO) count from their first step after activation, as documented, instead of from session start or the component's last reinforcer. Each component runs on its own clock, which stops while the component is inactive; a re-entered component resumes with the time it had accumulated. For example, `Chained([FR(5), FI(30.0)])` with one response per second now reinforces at 35 and 71 instead of 30 and 60. `Mixed` behaves the same way. New conformance fixture `compound/chained_fr2_fi5.json`.

## [0.1.1]

### Fixed

- The DSL bridge passes `@algorithm(seed=..., n=...)` to stochastic schedules, so seeded VI/VR/RI/RR/VT/RT schedules built from DSL source are reproducible.

### Changed

- Depend on `contingency-dsl-py` from PyPI instead of a direct git URL.
- Add a trusted-publishing workflow for PyPI.

## [0.1.0]

### Added

- Atomic schedules: FR, VR, RR, FI, VI, RI, FT, VT, RT, CRF, EXT.
- Compound schedules: Concurrent (with changeover delay), Multiple, Chained, Tandem, Alternative.
- Differential reinforcement: DRO (resetting, momentary), DRL, DRH.
- Progressive-ratio schedules (arithmetic, geometric, Hantula step functions) and Limited Hold.
- Trial-based and aversive schedule families.
- Fleshler-Hoffman VI/VR value generator, including the Hantula (1991) program variant.
- `ScheduleBuilder` and the DSL bridge `contingency.bridge.from_dsl`.
- Hardware abstraction layer `contingency.hw` with virtual, serial, and HIL bridge backends.
- Conformance fixtures under `conformance/` shared with the Rust implementation.

### Changed

- The concurrent-schedule changeover requirement is named Fixed-Ratio Changeover (`frco`).
